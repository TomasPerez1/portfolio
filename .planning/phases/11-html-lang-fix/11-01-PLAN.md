<objective>
Fix LOCALE-01: make `<html lang>` reflect the actual route locale (`en` on `/en`, `es` on `/es`), derived from the request — not from a `NEXT_LOCALE` cookie that is never set.

Purpose: A correct `<html lang>` per locale is a hard prerequisite for Phase 13 (hreflang/canonical symmetry depends on it) and is the LOCALE-01 acceptance.
Output: `my-app/src/proxy.ts` (relocated, renamed, sets `x-locale`), modified `my-app/src/app/layout.tsx` (reads `x-locale`, drops cookie read), deleted `my-app/src/app/middleware.ts`, human-verified production build.

| client → proxy (request headers) | A client could send an inbound `x-locale` header attempting to control `<html lang>`. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-01 | Spoofing/Tampering | `x-locale` request header (proxy → layout) | mitigate | Proxy ALWAYS does `new Headers(request.headers); set("x-locale", locale)` — `Headers.set()` overwrites any client-supplied value with the server-computed route locale, so an attacker-supplied `x-locale` cannot reach the layout. Value is bound to `i18n.locales` ∪ `"en"` fallback. |
| T-11-02 | Denial of Service | header size (431) | accept | `x-locale` is 2 chars; negligible. The docs' 431 warning concerns large headers only. |
| T-11-SC | Tampering | npm/pip/cargo installs | accept | Zero package installs in this phase (consistent with the milestone's "zero new npm dependencies" decision). No legitimacy gate needed. |
</threat_model>
